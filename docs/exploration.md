## C1 — SQLite Indexing Experiment

### Hypothesis
Adding a composite index on `(city, season)` will speed up the GROUP BY query
that aggregates pollution statistics by city and season, because SQLite can
scan the index rather than performing a full table scan.

### Method
1. Loaded the cleaned dataset (52,704 rows) into an in-memory SQLite database.
2. Ran the GROUP BY query **without** any index, 5 times, measured mean latency.
3. Created `CREATE INDEX idx_city_season ON air_quality (city, season)`.
4. Ran the same query **with** the index, 5 times, measured mean latency.
5. Used `EXPLAIN QUERY PLAN` to confirm index usage.

The query:

```sql
SELECT
    city,
    season,
    ROUND(AVG(pm2_5), 2)                                          AS avg_pm2_5,
    MAX(european_aqi)                                             AS peak_aqi,
    COUNT(*)                                                      AS total_hours,
    SUM(CASE WHEN aqi_category = 'Very High' THEN 1 ELSE 0 END)  AS very_high_hours
FROM air_quality
GROUP BY city, season
ORDER BY avg_pm2_5 DESC;
```

### Results

| Scenario          | Avg latency (ms) | EXPLAIN QUERY PLAN output               |
|-------------------|------------------|-----------------------------------------|
| Without index     | **35.14 ms**     | `SCAN air_quality` (full table scan)    |
| With index        | **13.01 ms**     | `SCAN air_quality USING INDEX idx_city_season` |

**Speedup: 2.7×**

The `EXPLAIN QUERY PLAN` output changes from:
```
SCAN air_quality
USE TEMP B-TREE FOR GROUP BY
USE TEMP B-TREE FOR ORDER BY
```
to:
```
SCAN air_quality USING INDEX idx_city_season
USE TEMP B-TREE FOR ORDER BY
```
The index eliminates the temporary B-Tree needed for GROUP BY, as SQLite can
iterate the index in `(city, season)` order directly.

### Discussion
For 52,704 rows the speedup is 2.7×. For a continuously-growing time-series feed
(months of hourly data) this benefit compounds — a full table scan grows O(n)
while the index-assisted scan stays closer to O(k · log n), where k is the number
of distinct (city, season) groups (24 here).

**Trade-off:** The index adds storage overhead (~6 % of table size for a covering
index on two string columns) and slows `INSERT` slightly. For a write-heavy streaming
feed, a partial index (e.g., only the most recent month) or a materialised summary
table may be a better choice.

## C2 — GitHub Actions CI/CD

### Purpose
The `.github/workflows/ci.yml` pipeline automates:
1. **Linting** — `ruff check src/ tests/` on every push and pull request.
2. **Unit tests** — `pytest tests/ --cov=src` with coverage XML upload.
3. **Pipeline smoke test** — runs `python -m src.run_part_a` if the raw data
   file is present, then checks all required source files exist.

### Workflow Design

```
push / PR  ──►  lint-and-test  ──►  pipeline-smoke-test
                (ruff + pytest)       (Part A end-to-end)
```

The two jobs are chained with `needs: lint-and-test` so the smoke test
only runs if tests pass. This prevents wasted minutes on a broken build.

### Why CI/CD Matters for a Data Pipeline
- **Reproducibility**: every collaborator runs the same Python version
  (`3.11`) and pinned dependencies (`requirements.txt`).
- **Fast feedback**: a 69-line ruff check catches style issues before
  code reaches `main`.
- **Coverage tracking**: the XML coverage report is uploaded as an artifact
  each run, making regression visible over time.
- **Data validation gate**: the smoke test would catch a regression in
  `validate_data.py` immediately — the SystemExit quality gate turns a
  silent data error into a CI failure.

### Key CI file: `.github/workflows/ci.yml`
See the full file at `.github/workflows/ci.yml` in the repository root.

## C3 — System Design Glossary

| Term | Definition | Relevance to this project |
|---|---|---|
| **Data Pipeline** | An ordered sequence of steps that move and transform data from a source to a destination. | Our pipeline: Open-Meteo API → CSV → clean → validate → analyse → model. |
| **ETL** | Extract, Transform, Load — the classic pattern for moving data from sources to a data warehouse. | `inspect_data.py` (E) + `clean_data.py` (T) + SQLite (L). |
| **Idempotency** | A pipeline is idempotent if running it multiple times produces the same result as running it once. | Our pipeline overwrites outputs each run → idempotent. |
| **Schema** | The formal description of a dataset's columns, types, and constraints. | Documented in `docs/schema.md`, auto-generated by `inspect_data.py`. |
| **Data Quality Gate** | A hard check that aborts the pipeline if data quality falls below a threshold. | `validate_data.py` raises `SystemExit` if pass rate < 95 %. |
| **Feature Engineering** | Creating new input variables from raw data to improve model performance. | `hour`, `month`, `season`, `time_of_day`, `is_weekend`, `aqi_category` derived in `clean_data.py`. |
| **sklearn Pipeline** | A scikit-learn object that chains preprocessing steps and a model so they are fitted and applied together. | `ColumnTransformer` + classifier in `train_model.py` — prevents data leakage. |
| **Winsorizing** | Capping outliers at a percentile boundary (here: IQR fences) instead of removing them. | Applied in `cap_outliers_iqr()` — preserves row count while reducing extreme values. |
| **EXPLAIN QUERY PLAN** | SQLite command that shows how the query optimizer will execute a query (which indexes it will use). | Used in C1 experiment to confirm index usage. |
| **CI/CD** | Continuous Integration / Continuous Delivery — automating build, test and deploy on every code change. | `.github/workflows/ci.yml` runs ruff + pytest on every push. |
| **Stratified Split** | Splitting data into train/test while preserving the class distribution of the target variable. | `train_test_split(..., stratify=y)` in `train_model.py`. |
| **Joblib** | Python library for efficient serialisation of large numpy arrays; standard way to save sklearn models. | `joblib.dump(pipeline, 'models/best_pipeline.joblib')` in `train_model.py`. |

## C4 — System Design: Scaling to 1 Million Rows per Day

### Context
The current pipeline processes 52,704 hourly rows for 6 cities over one year.
Suppose we scale to 100 cities with 5-minute readings: that is
`100 × 365 × 24 × 12 = 10,512,000` rows per year, or ~28,800 per hour.

### Proposed Architecture

```
┌─────────────────────────────────────────────────────────┐
│  DATA SOURCES                                           │
│  Open-Meteo API  ──►  HTTP collector (cron / GH Action) │
└───────────────────────────┬─────────────────────────────┘
                            │  raw JSON / CSV (S3 / Azure Blob)
                            ▼
┌─────────────────────────────────────────────────────────┐
│  INGESTION & VALIDATION                                 │
│  Kafka / Azure Event Hub  (message queue)               │
│  Schema validation  ──►  Dead-letter queue (bad rows)   │
└───────────────────────────┬─────────────────────────────┘
                            │  validated events
                            ▼
┌─────────────────────────────────────────────────────────┐
│  PROCESSING                                             │
│  Apache Spark / Pandas on Databricks                    │
│  - Cleaning (IQR cap, coord fix, feature engineering)   │
│  - Aggregation (city × season × hour summaries)         │
│  - Partitioned Parquet writes (by city + year-month)    │
└───────────────────────────┬─────────────────────────────┘
                            │  clean, partitioned Parquet
                            ▼
┌─────────────────────────────────────────────────────────┐
│  STORAGE                                                │
│  Data Lake (Azure ADLS / AWS S3)                        │
│  - raw/           ← original JSON (never overwrite)     │
│  - cleaned/       ← Parquet partitioned by city/month   │
│  - features/      ← ML-ready feature matrices           │
└──────────────┬──────────────────────────────────────────┘
               │                        │
               ▼                        ▼
┌─────────────────────┐   ┌─────────────────────────────┐
│  ANALYTICS          │   │  ML SERVING                 │
│  Azure Synapse SQL  │   │  MLflow model registry      │
│  Power BI dashboard │   │  Azure ML endpoint          │
│  Scheduled reports  │   │  Real-time AQI prediction   │
└─────────────────────┘   └─────────────────────────────┘
```

### Key Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Streaming vs. Batch | Micro-batch (every 15 min) | Air quality changes slowly; true streaming not needed. Reduces cost vs. real-time Kafka. |
| File Format | Parquet + columnar partitioning | 10× smaller than CSV for float-heavy data; predicate pushdown speeds city-filter queries. |
| Validation | Schema + quality gate at ingest | Catches bad rows early; dead-letter queue preserves them for manual review. |
| Model Serving | REST endpoint + batch scoring | Real-time for dashboard; batch for daily city reports. |
| Versioning | MLflow experiment tracking | Reproducibility across model versions; rollback if performance degrades. |

### Where Our Code Fits
- `clean_data.py` → Spark UDFs (each function becomes a column transformation).
- `validate_data.py` → Great Expectations / Pandera data contracts.
- `train_model.py` → MLflow `autolog()` wrapping the same sklearn Pipeline.
- `predict.py` → Azure ML managed endpoint (same joblib model, different invocation).
